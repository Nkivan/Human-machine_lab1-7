# Dogfight — Lab 01: The Event Loop Is the Game Loop

Корабель на canvas із фіксованим кроком симуляції (60 Hz) та інтерполяцією при рендері[cite: 12].

**Керування:** ←/→ або A/D — поворот, ↑ або W — тяга, H — показати/сховати HUD[cite: 12].

**Запуск:** `npm install`, потім `npm run dev`, відкрити `http://localhost:5173`[cite: 12].

## Структура

- `src/loop.js` — `createLoop`: rAF + clamped accumulator, статистика steps/s, frames/s, frame ms[cite: 12]
- `src/input.js` — `createInput`: замикання над станом клавіш (`isDown`, `justPressed`)[cite: 12]
- `src/sim/` — чиста симуляція (ship, arena, math), без DOM і canvas[cite: 12]
- `src/render/` — DPR-aware canvas і малювання[cite: 12]

## Налаштування керування (M2)

У `src/sim/ship.js` задано стартову точку по центру арени (`x: ARENA.width / 2, y: ARENA.height / 2`) з напрямком носа вгору (`angle: -Math.PI / 2`) та підібрано параметри `TUNING` для плавного й контрольованого польоту без залежності від DOM, canvas і джерела часу:
- `turnSpeed: 3.6` rad/s — забезпечує достатньо швидкий розворот корабля без різких смикань
- `thrustAccel: 380` px/s² — дає відчутне прискорення вздовж курсу (`Math.cos(ship.angle)`, `Math.sin(ship.angle)`) при ввімкненій тязі
- `drag: 0.6` 1/s — експоненційне загасання (`Math.exp(-TUNING.drag * dt)`) гасить швидкість після відпускання тяги, щоб корабель не ковзав занадто довго без контролю
- `maxSpeed: 520` px/s — обмежує граничну швидкість корабля, зберігаючи керованість на арені з `wrap(ship)`

## Базові виміри

Монітор 75 Hz: HUD показує steps/s = 60.0, frames/s = 75.0, frame ms = 13.3[cite: 12].
Симуляція крокує по 60 разів за секунду незалежно від частоти екрана[cite: 12].

## Експеримент 1 — блокування 100 мс у render кожен 60-й кадр

**Що змінено:** у `render` кожну 60-ту ітерацію виконується `while (performance.now() < t + 100) {}`[cite: 12].

**Що видно:** приблизно раз на секунду корабель на мить зупиняється й ривком стрибає вперед[cite: 12].

**Цифри HUD:** frames/s впали з 75.0 до 69.0; steps/s лишилися 60.0; frame ms на один кадр стрибає до ~113 мс[cite: 12].

**Пояснення:** JavaScript виконується в одному потоці й за моделлю run-to-completion[cite: 12]. Поки `render` крутить синхронний цикл, стек викликів зайнятий, і цикл подій не може взяти наступну задачу: ні наступний rAF, ні події клавіатури, ні перемальовування сторінки[cite: 12]. Жоден інший JS-код не може перервати цей цикл, тому блок неможливо «обійти» з JavaScript на тому самому потоці[cite: 12]. Накопичувач лише наздоганяє пропущені кроки симуляції (~7 за один кадр), тому стан гри лишається правильним, але втрачений час відображення повернути не можна[cite: 12]. Єдине рішення — винести важку роботу в окремий потік (Web Worker)[cite: 12].

## Експеримент 2 — setInterval(frame, 16) замість requestAnimationFrame

**Що змінено:** у `loop.js` rAF замінено на `setInterval(() => frame(performance.now()), 16)`[cite: 12].

| | steps/s | frames/s | frame ms |[cite: 12]
|---|---|---|---|
| setInterval(16) | 59.5 | 62.5 | 16.1 |[cite: 12]
| requestAnimationFrame | 60.0 | 75.0 | 13.5 |[cite: 12]

Консольний звіт за 10 с (включає короткі паузи від перемикання вкладки, тому max завищений)[cite: 12]:

- setInterval(16): 554 кадри, fps ≈ 55.4, min 5.5 мс, max 764.8 мс, avg 18.05 мс[cite: 12]
- rAF: 694 кадри, fps ≈ 69.4, min 12.9 мс, max 386.9 мс, avg 14.4 мс[cite: 12]

**Фонова вкладка (5 с):** виклики `frame()`, поки вкладка була прихована: setInterval — 43, rAF — 34[cite: 12]. Для rAF очікувалось близько нуля; ймовірно, кілька колбеків спрацювали на межі перемикання вкладки[cite: 12].

**Висновок:** таймер на 16 мс дає ~62.5 кадра/с (1000/16), не знає про частоту дисплея (75 Hz), і його виклики не вирівняні з оновленням екрана; навіть steps/s просідають до 59.5[cite: 12]. Три причини, чому rAF кращий: (1) синхронізація з дисплеєм — виклик перед кожним paint; (2) у прихованій вкладці браузер призупиняє rAF, а таймер продовжує працювати вхолосту (лише сповільнений); (3) 16 ≠ 16.667, тому таймери дрейфують і дають нерівномірні кадри[cite: 12].

## Експеримент 3 — без accumulator (змінний крок) та CPU throttling 6×

**Тест:** корабель автоматично «тримає» тягу; через ~5 секунд утримання тяги виводиться позиція[cite: 12].

| | без тротлінгу | з тротлінгом 6× |[cite: 12]
|---|---|---|
| змінний крок: `simulate(dt)` раз на кадр | y=409.104, 329 кроків | y=462.810, 273 кроки |[cite: 12]
| фіксований крок (accumulator) | y=462.119, 300 кроків | y=462.119, 300 кроків |[cite: 12]

(x = 640.000 в усіх запусках, бо корабель летить по вертикалі.)[cite: 12]

**Пояснення:** при змінному кроці `dt` дорівнює реальній тривалості кадру, а інтегрування за Ейлером залежить від розміру кроку[cite: 12]. На різній швидкості CPU кадри різні, тому за ті самі ~5 секунд утримання тяги корабель опиняється в різних місцях, а кількість кроків теж різна[cite: 12]. З фіксованим кроком симуляція завжди виконує рівно 300 кроків по 1/60 с (5 секунд симуляційного часу), тому результат однаковий незалежно від швидкості машини[cite: 12]. Це детермінізм: однакові входи дають однаковий результат[cite: 12]. У мультиплеєрі (Lab 5) клієнт і сервер мають окремо виконувати ті самі кроки й отримувати однаковий стан, інакше їхні світи розійдуться[cite: 12].
