# Dogfight — Lab 01: The Event Loop Is the Game Loop

Корабель на canvas із фіксованим кроком симуляції (60 Hz) та інтерполяцією при рендері.

**Керування:** ←/→ або A/D — поворот, ↑ або W — тяга, H — показати/сховати HUD.

**Запуск:** `npm install`, потім `npm run dev`, відкрити `http://localhost:5173`.

## Структура

- `src/loop.js` — `createLoop`: rAF + clamped accumulator, статистика steps/s, frames/s, frame ms
- `src/input.js` — `createInput`: замикання над станом клавіш (`isDown`, `justPressed`)
- `src/sim/` — чиста симуляція (ship, arena, math), без DOM і canvas
- `src/render/` — DPR-aware canvas і малювання

## Налаштування керування (M2)

У `src/sim/ship.js` задано стартову точку по центру арени (`x: ARENA.width / 2, y: ARENA.height / 2`) з напрямком носа вгору (`angle: -Math.PI / 2`) та підібрано параметри `TUNING` для плавного й контрольованого польоту без залежності від DOM, canvas і джерела часу:

- `turnSpeed: 3.6` rad/s — забезпечує достатньо швидкий розворот корабля без різких смикань
- `thrustAccel: 380` px/s² — дає відчутне прискорення вздовж курсу (`Math.cos(ship.angle)`, `Math.sin(ship.angle)`) при ввімкненій тязі
- `drag: 0.6` 1/s — експоненційне загасання (`Math.exp(-TUNING.drag * dt)`) гасить швидкість після відпускання тяги, щоб корабель не ковзав занадто довго без контролю
- `maxSpeed: 520` px/s — обмежує граничну швидкість корабля, зберігаючи керованість на арені з `wrap(ship)`

## Базові виміри

Монітор 75 Hz: HUD показує steps/s = 60.0, frames/s = 75.0, frame ms = 13.3.
Симуляція крокує по 60 разів за секунду незалежно від частоти екрана.

## Експеримент 1 — блокування 100 мс у render кожен 60-й кадр

**Що змінено:** у `render` кожну 60-ту ітерацію виконується `while (performance.now() < t + 100) {}`.

**Що видно:** приблизно раз на секунду корабель на мить зупиняється й ривком стрибає вперед.

**Цифри HUD:** frames/s впали з 75.0 до 69.0; steps/s лишилися 60.0; frame ms на один кадр стрибає до ~113 мс.

**Пояснення:** JavaScript виконується в одному потоці й за моделлю run-to-completion. Поки `render` крутить синхронний цикл, стек викликів зайнятий, і цикл подій не може взяти наступну задачу: ні наступний rAF, ні події клавіатури, ні перемальовування сторінки. Жоден інший JS-код не може перервати цей цикл, тому блок неможливо «обійти» з JavaScript на тому самому потоці. Накопичувач лише наздоганяє пропущені кроки симуляції (~7 за один кадр), тому стан гри лишається правильним, але втрачений час відображення повернути не можна. Єдине рішення — винести важку роботу в окремий потік (Web Worker).

## Експеримент 2 — setInterval(frame, 16) замість requestAnimationFrame

**Що змінено:** у `loop.js` rAF замінено на `setInterval(() => frame(performance.now()), 16)`.

| | steps/s | frames/s | frame ms |
|---|---|---|---|
| `setInterval(16)` | 59.5 | 62.5 | 16.1 |
| `requestAnimationFrame` | 60.0 | 75.0 | 13.5 |

Консольний звіт за 10 с (включає короткі паузи від перемикання вкладки, тому max завищений):

- `setInterval(16)`: 554 кадри, fps ≈ 55.4, min 5.5 мс, max 764.8 мс, avg 18.05 мс
- `rAF`: 694 кадри, fps ≈ 69.4, min 12.9 мс, max 386.9 мс, avg 14.4 мс

**Фонова вкладка (5 с):** виклики `frame()`, поки вкладка була прихована: `setInterval` — 43, `rAF` — 34. Для `rAF` очікувалось близько нуля; ймовірно, кілька колбеків спрацювали на межі перемикання вкладки.

**Висновок:** таймер на 16 мс дає ~62.5 кадра/с (1000/16), не знає про частоту дисплея (75 Hz), і його виклики не вирівняні з оновленням екрана; навіть steps/s просідають до 59.5. Три причини, чому rAF кращий: (1) синхронізація з дисплеєм — виклик перед кожним paint; (2) у прихованій вкладці браузер призупиняє rAF, а таймер продовжує працювати вхолосту (лише сповільнений); (3) 16 ≠ 16.667, тому таймери дрейфують і дають нерівномірні кадри.

## Експеримент 3 — без accumulator (змінний крок) та CPU throttling 6×

**Тест:** корабель автоматично «тримає» тягу; через ~5 секунд утримання тяги виводиться позиція.

| | без тротлінгу | з тротлінгом 6× |
|---|---|---|
| змінний крок: `simulate(dt)` раз на кадр | `y=409.104`, 329 кроків | `y=462.810`, 273 кроки |
| фіксований крок (accumulator) | `y=462.119`, 300 кроків | `y=462.119`, 300 кроків |

(`x = 640.000` в усіх запусках, бо корабель летить по вертикалі.)

**Пояснення:** при змінному кроці `dt` дорівнює реальній тривалості кадру, а інтегрування за Ейлером залежить від розміру кроку. На різній швидкості CPU кадри різні, тому за ті самі ~5 секунд утримання тяги корабель опиняється в різних місцях, а кількість кроків теж різна. З фіксованим кроком симуляція завжди виконує рівно 300 кроків по 1/60 с (5 секунд симуляційного часу), тому результат однаковий незалежно від швидкості машини. Це детермінізм: однакові входи дають однаковий результат. У мультиплеєрі (Lab 5) клієнт і сервер мають окремо виконувати ті самі кроки й отримувати однаковий стан, інакше їхні світи розійдуться.
