# Dogfight — Лабораторна робота №06: TypeScript

Уся кодова база (`shared`, `server`, `client`) переведена на TypeScript у суворому режимі (`strict` + `noUncheckedIndexedAccess` + `verbatimModuleSyntax` + `erasableSyntaxOnly`) з єдиним типізованим протоколом і валідацією даних на всіх межах[cite: 1, 2]. Поведінка під час виконання (runtime) залишилася незмінною: хеш детермінізму з Лабораторної №05 ідентичний (`e34f5d00`), що підтверджується автоматичним тестом[cite: 1, 2].

## Запуск та перевірка

```bash
npm install                 # Рекомендовано Node 22; працює на Node >= 20.6 (сервер запускається через tsx)
npm run dev:server          # Термінал 1 -> [http://127.0.0.1:3000](http://127.0.0.1:3000)
npm run dev:client          # Термінал 2 -> http://localhost:5173 (відкрити у ДВОХ вікнах і зайти в одну кімнату)
npm run typecheck           # tsc --noEmit у кожному воркспейсі (Vite не виконує перевірку типів)
npm run lint                # typescript-eslint: заборонено any, non-null ! та зайві as-касти
npm test                    # Усі тести (shared, client, server)
npm run build               # Збірка клієнта через Vite
npm run bench               # Бенчмарк JSON (Zod) проти Binary (DataView)
```

Запуск сервера нативним TypeScript без `tsx` (Node >= 22.18 або 22.6+ із прапорцем): `npm run start:native -w server`[cite: 2].  
Керування та URL-прапорці збережені з Лабораторної №05 (`?lat=100&jitter=30&drop=0.02`, `?noise=4`, `?hash=1`, а також **`?codec=json`** для перемикання на JSON-кодек)[cite: 2].

CI (`.github/workflows/ci.yml`) автоматично виконує `npm ci && npm run typecheck && npm run lint && npm test && npm run build`[cite: 1, 2].

## Що змінилося (та чому)

| Модуль / Файл | Зміни та архітектурне обґрунтування |
|---|---|
| `tsconfig.base.json` | Увімкнено `strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`, `verbatimModuleSyntax`, `erasableSyntaxOnly` (без `enum` та parameter properties для підтримки нативного Type Stripping у Node.js), `noUnused*`[cite: 2]. |
| `shared/` | Компілюється без типів DOM і Node (`"types": []`), що гарантує незалежність симуляції від середовища виконання[cite: 2]. `Vector2` має `readonly x, y`; `EntityId`, `Tick`, `Seq` — брендовані типи; `Ship \| Bullet \| Asteroid \| Pickup` — розмічене об'єднання (discriminated union) за полем `kind`[cite: 1, 2]. |
| `shared/src/protocol/messages.ts` | Єдине джерело істини: Zod-схеми -> виведені TS-типи -> парсери часу виконання для всіх JSON-повідомлень в обидва боки, знімків стану та HTTP API[cite: 2]. `parseClientMessage(data: unknown): Result` ніколи не кидає винятків; ручний валідатор із Лабораторної №04 видалено[cite: 2]. |
| `shared/src/codec/` | Бінарний декодер повертає `Result` без винятків; старший напівбайт першого байта містить версію протоколу (`PROTOCOL_VERSION = 2`) для відсіювання застарілих клієнтів; реалізовано інтерфейс `Codec` із бінарною та JSON-реалізаціями[cite: 1, 2]. |
| `shared/src/bus.ts` | Типізована шина подій `Bus<E>` замінила `EventTarget + CustomEvent` (де `detail` мав тип `any`) у симуляції, аудіомодулі, HUD та лобі[cite: 2]. |
| `server/src/config.ts` | Змінні середовища валідуються через Zod-схему зі значеннями за замовчуванням, приведенням типів і миттєвою зупинкою при некоректній конфігурації[cite: 3]. |
| `server/src/rooms.ts` | `Room` наслідує узагальнений `EventEmitter<RoomEvents>` у Node.js, завдяки чому типи аргументів слухачів перевіряються на етапі компіляції[cite: 3]. |
| `client/` | Усі зовнішні дані (`manifest.json`, `/api/rooms`, текстові та бінарні WebSocket-фрейми) типізуються як `unknown` і проходять валідацію перед використанням[cite: 3]. |

**Механічні обмеження (ESLint):** у всьому репозиторії **0** використань `any`, **0** операторів `!` (non-null assertion) і лише **3** приведення `as` — усі три зосереджені в `shared/src/protocol/ids.ts` у функціях-конструкторах брендованих типів (`asEntityId`, `asTick`, `asSeq`), оскільки бренд існує лише на рівні системи типів[cite: 1, 3].

## Що виявив TypeScript під час міграції (What TypeScript found)

1. **Небезпечна індексація масивів та словників (`noUncheckedIndexedAccess`)**: звернення `list[i]` у циклі колізій, `pending[0]`, `snaps[i]`, `particles[i]`, `PRESETS[preset]`, `assets.images["sheet"]` тепер мають тип `T | undefined`[cite: 3]. Там, де JS мовчки припускав існування елемента, додано явні перевірки[cite: 3].
2. **Необроблений `null` під час завантаження ресурсів**: завантажене зображення має тип `ImageBitmap | null` (опціональні асети повертають `null` при помилці)[cite: 3]. У `startNetGame` додано явну перевірку та зрозумілу помилку при відсутності спрайт-листа замість передачі `null` у `drawImage`[cite: 3].
3. **Нетипізовані корисні навантаження подій (`CustomEvent`)**: раніше `CustomEvent.detail` мав тип `any`, і помилка в імені поля (наприклад, `detail.shipid`) виявлялася лише в runtime як `undefined`[cite: 3]. Із `Bus<E>` ім'я події жорстко визначає тип об'єкта `payload`[cite: 3].
4. **Довільні властивості на сторонніх об'єктах**: у Лабораторній №05 лічильник пропущених пінгів зберігався як `socket.missed` безпосередньо на об'єкті WebSocket[cite: 3]. TypeScript заборонив розширення стороннього типу, тому стан перенесено в `WeakMap<WebSocket, number>`[cite: 3].
5. **Звуження діапазону керування поворотом (`turn`)**: замість загального `number` використано літеральний тип `-1 | 0 | 1`[cite: 3]. Бінарний декодер звужує значення через перевірки `!==`, а клієнт обчислює напрямок виразом `left === right ? 0 : right ? 1 : -1`, виключаючи некоректні значення на кшталт `turn: 100`[cite: 1, 3].
6. **Дублювання «магічних чисел» протоколу**: коди типів сутностей (`1..4`), бітові прапорці та пакування поля `aux` раніше повторювалися в енкодері, декодері та рендерері[cite: 1, 3]. Тепер вони інкапсульовані в `codec/binary.ts`, а решта коду працює з типізованими полями (`{ kind: "ship", hp, cooldown, thrust, rapid, shield, homing }`)[cite: 1, 3].
7. **Конфлікт типів середовища в `shared/`**: перевірка `typeof window` у спільному пакеті не скомпілювалася через відсутність DOM-типів — замінено на середовищно-незалежну перевірку `"window" in globalThis`[cite: 3].

## Три найцікавіші типи в проєкті

1. **Розмічене об'єднання та вичерпний `switch` (`EntityRecord` у `shared/src/protocol/messages.ts`)**[cite: 1, 3]  
   Тип `EntityRecord` об'єднує чотири варіанти сутностей: `ShipRecord | BulletRecord | AsteroidRecord | PickupRecord`, кожен із яких має унікальне літеральне поле `kind` (`"ship"`, `"bullet"`, `"asteroid"`, `"pickup"`)[cite: 1, 3]. Перевірка `switch (e.kind)` автоматично звужує тип у кожній гілці (наприклад, `e.hp` чи `e.shield` доступні лише для `"ship"`, а `e.pickupType` — лише для `"pickup"`)[cite: 1, 3]. Кожен `switch` завершується гілкою `default: return assertNever(e)`, що гарантує помилку компіляції при додаванні нового типу сутності без оновлення всіх обробників[cite: 1, 3].

2. **Узагальнена типізована шина подій (`Bus<E>` у `shared/src/bus.ts`)**[cite: 1, 4]  
   ```ts
   on<K E extends keyof>(name: K, fn: (payload: E[K]) => void): () => void
   emit<K E extends keyof>(name: K, payload: E[K]): void
   ```
   Параметр типу `K extends keyof E` обмежує назву події ключами інтерфейсу подій (наприклад, `LobbyEvents` або `GameEvents`), а індексований доступ `E[K]` автоматично підставляє відповідний тип аргументу для цієї події[cite: 1, 4]. Завдяки цьому компілятор одразу підказує поля `payload` у колбеку `on()` і не дозволяє викликати `emit()` із неповним або неправильним об'єктом даних[cite: 4].

3. **Брендовані типи (`Brand<T, B>` у `shared/src/protocol/ids.ts`)**[cite: 1, 4]  
   ```ts
   declare const brand: unique symbol;
   export type Brand<T, B extends string> = T & { readonly [brand]: B };
   export type EntityId = Brand<number, "EntityId">;
   export type Tick = Brand<number, "Tick">;
   export type Seq = Brand<number, "Seq">;
   ```
   У звичайному JS/TS ідентифікатор сутності, номер тіку та порядковий номер вводу є числами (`number`), тому їх легко випадково переплутати місцями у виклику функції[cite: 4]. Брендування додає віртуальну властивість із `unique symbol`, яка повністю стирається після компіляції (нульові витрати в runtime), але на етапі перевірки типів забороняє передати `Tick` туди, де очікується `Seq` або `EntityId`[cite: 1, 4].

## Рішення щодо UI-фреймворку (M4)

Лобі, чат та HUD реалізовані **без використання зовнішнього UI-фреймворку** (React/Vue/Svelte) — на чистому типізованому DOM API за допомогою власної утиліти `el<K extends keyof HTMLElementTagNameMap>()` (`client/src/dom.ts`) та типізованої шини подій `Bus<LobbyEvents>` (`client/src/lobby.ts`, `client/src/lobbyView.ts`, `client/src/hud.ts`)[cite: 1, 4].

**Обґрунтування:**
* Ігровий `canvas` та цикл рендерингу (`loop.ts`, `draw.ts`) у будь-якому разі залишаються ванільними для збереження продуктивності та контролю кадрів[cite: 4].
* Весь інтерфейс лобі й HUD займає близько 80–120 рядків прозорого типізованого коду, де стан відокремлено від рендерингу через `Lobby` + `Bus`[cite: 4].
* Підключення фреймворку додало б рантайм-залежність і ускладнило б конфігурацію збірки/тестів сильніше, ніж обсяг коду, який воно замінює[cite: 4].

## Вимірювання продуктивності протоколу (`npm run bench`)

Умови тесту: 4 гравці, частота 30 Гц, 21 сутність у знімку (`4` кораблі + астероїди + снаряди), після додавання підсилень (`pickup`) та розширення бінарного запису сутності з 24 до 28 байтів (`11 + 28 * 21 = 599` байтів на знімок)[cite: 1, 5]:

| Кодек | Байтів / знімок | KB/s на клієнта (down) | KB/s на клієнта (up) | Snapshot enc+dec (мкс) | Input enc+dec (мкс) |
|---|---:|---:|---:|---:|---:|
| JSON (валідація Zod) | 3815 | 111.8 | 4.1 | 154.3 | 5.8 |
| Binary (DataView) | 599 | 17.5 | 0.6 | 14.0 | 1.9 |

Бінарний формат зменшує вхідний трафік клієнта у **6.4 раза** (`111.8` проти `17.5` KB/s), вихідний — у **7.0 раза** (`4.1` проти `0.6` KB/s), а повний цикл кодування й декодування знімка з валідацією/парсингом виконується приблизно в **11 разів** швидше (`14.0` мкс проти `154.3` мкс у JSON + Zod).

## Підсилення (Pickups / Power-ups)

У кімнатах із увімкненим параметром `pickupEvery` (зокрема у стартових кімнатах `alpha` та `bravo`; `0` — вимкнено) періодично з'являються три типи підсилень[cite: 5]. Одночасно на арені може існувати не більше двох підсилень, кожне зникає через 12 с, якщо його не підібрати[cite: 5]:

| Підсилення | Літера | Ефект | Де виконується |
|---|---|---|---|
| `shield` | **S** (синій) | Неуразливість до пошкоджень на 6 с (180 кроків)[cite: 5] | Лише сервер (`Ship.damage`)[cite: 5] |
| `rapid` | **R** (жовтий) | Зменшення затримки пострілу з 9 до 3 кроків на 8 с (240 кроків)[cite: 5] | Спільний `stepShip` (клієнтське передбачення має знати про зміну темпу стрільби)[cite: 5] |
| `homing` | **H** (рожевий) | Снаряди самонаводяться на найближчу ціль протягом 8 с (240 кроків)[cite: 5] | Лише сервер (поведінка наведення прив'язується до снаряда)[cite: 5] |

Активні ефекти відображаються у HUD (`SHIELD 4s RAPID 7s`), щит малюється як контур навколо корабля, а самонавідні снаряди мають рожевий колір[cite: 5].

**Вплив на протокол і роль системи типів:**  
Додавання четвертого типу сутності `"pickup"` та полів ефектів корабля (`rapid`, `shield`, `homing`) автоматично спричинило помилки компіляції в кожному `switch` за `EntityRecord` / `AnyEntity` через `assertNever`, що не дозволило забути про оновлення бінарного енкодера, декодера або рендерера[cite: 1, 5]. Розмір однієї сутності у бінарному кадрі зріс із 24 до 28 байтів (3 байти лічильників ефектів у кроках `1/30 с` + 1 зарезервований байт)[cite: 1, 5].
